# Fixture assets

Files `seed.sh` copies rather than generates.

Everything else in the fixture is built from scratch by ImageMagick and ffmpeg, which is
the better default: a generated tree is reviewable, cannot drift, and adds no binaries to
the repo. Something only lands here when generating it would cost more than it is worth.

## `portrait-with-exif-thumbnail.jpg`

A 900x1200 purple gradient carrying an embedded EXIF (IFD1) thumbnail of 1400 bytes, with
orientation 6 — a quarter turn clockwise.

It covers the fast path in `LocalImageThumbnailSource`: the app reads the first ~128 KB of a
photo and lifts out the thumbnail the camera already wrote, instead of transferring the
whole file to draw a 128 px tile. The other fixture images carry no EXIF at all, so between
them both routes through that class are exercised. Orientation 6 is deliberate — the source
is portrait with a top-to-bottom gradient, so a correctly rotated thumbnail shows as
landscape with the gradient running left to right, and a regression in rotation is visible
at a glance rather than subtly wrong.

**Why it is committed.** Neither ImageMagick nor ffmpeg can write an IFD1 thumbnail. Doing
it in the seed script meant assembling the APP1 segment by hand, which pulled a language
runtime into a script that otherwise needs two image tools — too much dependency for test
data.

**How to rebuild it**, should it ever need to change:

```python
# python3, standard library only. Takes the full-size JPEG and the thumbnail JPEG,
# and writes the full-size one back with the thumbnail spliced into an APP1 segment.
#   magick -size 900x1200 gradient:purple-white photo.jpg
#   magick -size 120x160  gradient:purple-white thumb.jpg
import struct, sys

photo_path, thumb_path = sys.argv[1], sys.argv[2]
photo = open(photo_path, "rb").read()
thumb = open(thumb_path, "rb").read()

ORIENTATION_ROTATE_90 = 6

def entry(tag, type_, value):
    # A SHORT value is left-justified within the 4-byte value field; a LONG fills it.
    packed = struct.pack(">H", value) + b"\0\0" if type_ == 3 else struct.pack(">I", value)
    return struct.pack(">HHI", tag, type_, 1) + packed

ifd0 = struct.pack(">H", 1) + entry(0x0112, 3, ORIENTATION_ROTATE_90)
ifd0_end = 8 + len(ifd0) + 4          # TIFF header, IFD0, pointer to IFD1
thumb_offset = ifd0_end + 2 + 12 * 2 + 4

ifd1 = (
    struct.pack(">H", 2)
    + entry(0x0201, 4, thumb_offset)  # JPEGInterchangeFormat
    + entry(0x0202, 4, len(thumb))    # JPEGInterchangeFormatLength
    + struct.pack(">I", 0)            # no further IFD
)

# Offsets are relative to the start of the TIFF header, per TIFF 6.0.
tiff = b"MM\x00\x2a" + struct.pack(">I", 8) + ifd0 + struct.pack(">I", ifd0_end) + ifd1 + thumb
app1 = b"Exif\x00\x00" + tiff
segment = b"\xff\xe1" + struct.pack(">H", len(app1) + 2) + app1

with open(photo_path, "wb") as out:
    out.write(photo[:2] + segment + photo[2:])
```

Two things about the format are easy to get wrong and fail silently, so they are worth
keeping in mind if this is ever regenerated by other means:

- Offsets inside the TIFF block are relative to the **start of the TIFF header**, not to
  the file. The reader has to add the position of the APP1 payload back on.
- The thumbnail must be a complete JPEG in its own right, `ff d8` through `ff d9`. A wrong
  offset still yields bytes of the right length, so nothing notices until the decode fails.
